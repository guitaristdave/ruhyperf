# Механизм ConfigProvider

Механизм `ConfigProvider` — ключевая архитектурная основа модульности Hyperf. Именно благодаря ему достигается полное разделение компонентов, их независимость и возможность повторного использования в сторонних проектах.

## Что такое ConfigProvider?

Каждый компонент предоставляет специальный класс `ConfigProvider` (обычно размещаемый в корне пространства имен пакета). Этот класс возвращает всю необходимую конфигурацию компонента: сопоставления зависимостей для DI-контейнера, слушатели событий, консольные команды, правила публикации файлов конфигурации и директории сканирования аннотаций.

При старте приложения Hyperf автоматически считывает все зарегистрированные `ConfigProvider` и объединяет их настройки с основной конфигурацией приложения (`Hyperf\Contract\ConfigInterface`).

Класс `ConfigProvider` не имеет обязательных зависимостей, не наследует абстрактные классы и не реализует интерфейсов. Ему требуется лишь магический метод `__invoke(): array`, возвращающий массив настроек.

## Определение класса ConfigProvider

```php
<?php

namespace Hyperf\Foo;

class ConfigProvider
{
    public function __invoke(): array
    {
        return [
            // Автоматически объединяется с config/autoload/dependencies.php
            'dependencies' => [],
            
            // Настройки сканирования аннотаций (config/autoload/annotations.php)
            'annotations' => [
                'scan' => [
                    'paths' => [
                        __DIR__,
                    ],
                ],
            ],
            
            // Консольные команды компонента (config/autoload/commands.php)
            'commands' => [],
            
            // Слушатели событий (config/autoload/listeners.php)
            'listeners' => [],
            
            // Файлы для публикации командой vendor:publish
            'publish' => [
                [
                    'id' => 'config',
                    'description' => 'Описание файла конфигурации.',
                    'source' => __DIR__ . '/../publish/file.php',
                    'destination' => BASE_PATH . '/config/autoload/file.php',
                ],
            ],
            
            // Любые другие произвольные ключи конфигурации для ConfigInterface
        ];
    }
}
```

## Публикация конфигурационных файлов компонента

Если в `ConfigProvider` определен раздел `publish`, пользователи компонента могут скопировать файл конфигурации в свой проект командой:

```bash
php bin/hyperf.php vendor:publish hyperf/foo
```

## Регистрация ConfigProvider в composer.json

Чтобы фреймворк Hyperf обнаружил ваш `ConfigProvider`, добавьте запись в секцию `extra.hyperf.config` в файле `composer.json` компонента:

```json
{
    "name": "hyperf/foo",
    "require": {
        "php": ">=8.1"
    },
    "autoload": {
        "psr-4": {
            "Hyperf\\Foo\\": "src/"
        }
    },
    "extra": {
        "hyperf": {
            "config": "Hyperf\\Foo\\ConfigProvider"
        }
    }
}
```

После редактирования `composer.json` выполните `composer dump-autoload`, чтобы Composer обновил метаданные.

## Правила проектирования компонентов Hyperf

Поскольку блок `extra` в `composer.json` игнорируется другими PHP-фреймворками, `ConfigProvider` не создает конфликтов вне экосистемы Hyperf. При разработке компонентов важно соблюдать следующие правила:

1. **Совместимость со стандартным ООП**: Базовые классы компонента должны поддерживать использование в любых PHP-проектах без Hyperf. Специфичные для Hyperf возможности должны выноситься в отдельные классы-адаптеры.
2. **Соблюдение стандартов PSR**: При внедрении зависимостей всегда опирайтесь на интерфейсы стандартов PSR (PSR-7, PSR-11, PSR-14, PSR-15, PSR-16 и т.д.), либо интерфейсы контрактов `hyperf/contract`. Не завязывайтесь на конкретные классы реализации.
3. **Необязательные зависимости (suggest)**: Зависимости, специфичные для Hyperf (например, поддержка аннотаций или AOP), следует выносить в секцию `suggest` файла `composer.json`, а не в `require`.
4. **Конструкторное внедрение зависимостей**: Внутри самого компонента не используйте аннотацию `#[Inject]` — используйте классическое внедрение зависимостей через конструктор (`__construct`).
5. **Безопасность корутин (Stateless)**: Избегайте хранения изменяемого состояния запроса в свойствах объектов-синглтонов или статических свойствах классов. Состояние конкретного запроса должно сохраняться через контекст корутины (`Hyperf\Context\Context`).
